# 口语对话实战器 · 发布前检查

一条命令跑完 **20 项**，逐项给 PASS/FAIL 和**实际值**。真源（每项的命令、通过标准、出处、误报风险）在
`references/checks.md`；`scripts/check.sh` 是它的可执行实现 —— **两者不一致时以 `references/checks.md` 为准**。

## 什么时候用

- **部署前**（`tcb fn deploy` / `tcb hosting deploy` 之前）
- **交付前**（要给打卡截图、要给队友或评审看之前）
- 改过云函数 / 接口契约 / 前端 JS 之后
- 换机器、隔了一段时间回来接着做时

**不适用**：把检查本身做成自动化流水线（Day 25 已拍板不做，理由见「已定事项」）。

## 怎么跑

```bash
# 1) 第 13 项要跑无头回归，先把本地服务起起来（另开一个终端，让它开着）
cd frontend && python serve.py

# 2) 回仓库根目录，跑检查
bash .workbuddy/skills/kouyu-verify-project/scripts/check.sh
```

**★ 必须在 Git Bash / MINGW64 里跑**（脚本用了 bash 特有的 `$'…'`、进程替换 `<()`；PowerShell 跑不了）。

可选：换环境时用环境变量覆盖基址，不用改脚本。

```bash
TALK_BASE=https://别的域名 bash .workbuddy/skills/kouyu-verify-project/scripts/check.sh
```

**退出码 = 失败数 + 跳过数**。★ 跳过不算通过 —— 它意味着「这一项没有拿到证据」。

## 输出长什么样

```
[ 1/20] PASS 仓库里没有真实密钥                    实际值：全量 2 条全在白名单内…
[ 7/20] FAIL 跨域头存在（必须带 Origin 才问得出）   实际值：带 Origin 也没拿到 access-control-allow-origin…
通过 18 / 失败 1 / 跳过 1
跳过项不算通过：它意味着「这一项没有拿到证据」
```

## 20 项一览

| 组 | 项 | 项数 |
|---|---|---|
| 1 密钥与仓库卫生 | 仓库无真密钥 / 历史无真密钥 / 无连接串密码 / `.env` 忽略规则 / 被跟踪的密钥类文件 | 5 |
| 2 公网与接口 | 接口存活与外壳 / **跨域头（带 Origin）** / 非法参数被挡 / 404·405 是自家 JSON / 首页不是拦截页 | 5 |
| 3 环境变量 | **必需 7 个键齐（控制台）** / 缺变量明确报错 | 2 |
| 4 前端静态与运行时 | JS 语法 + 五页五断点回归 / 内联注释配对 / 不引用已删错误码 | 3 |
| 5 数据口径与契约 | count 是整数 / B6 `endedAt=null` / B7 两条硬约束 / 错误码 ↔ §1.4 / 前端映射表覆盖 | 5 |

「本地开发注意」两条（必须走 `serve.py`、`curl --noproxy '*'`）不占编号，附在输出末尾。

## 三条「不虚报」机制（这是这个 Skill 存在的理由）

写检查器最容易犯的错，是让它**在什么都没验到的时候报绿**。所以：

1. **每一项都打印实际值**，不只打 PASS。看不到值的 PASS 等于没验。
2. **取不到值 → 判 FAIL 或跳过，绝不判 PASS。** 上游静默失败是这类检查最大的敌人 ——
   本项目已经吃过两次：`verify.sh` 的 `getf` 语义写反（差点把库里昵称写成空）、
   `friendlyMessage` 兜底原样回吐英文码。
3. **白名单显式写在脚本里**，命中要打印「为什么安全」。
   判据是「**每一条都确认过安全**」，不是「一条都没有」——
   后者会逼着人删掉单测需要的官方示例值与给人看的占位符。

另外三条防自欺的：

- **脚本会自检项数**：跑完若项数不等于 20，按失败计（漏跑一项也会被发现）。
- **不要相信退出码**：`frontend/regress.js` 永远 `exit 0`，`curl` 对拦截页也返回 200 ——
  所以第 10、13 项的判据都是**解析输出文本**，不是看退出码。
- **判据要锚定到「行 / 规则 / 语法位置」，别浮在「字符串出现过」这一层。** 首跑实测出来的三条：
  查忽略规则要加 `git check-ignore --no-index`（否则**对已跟踪的文件永远问不出真话**）；
  搜代码要先**剥注释**（否则注释里解释历史的文字被当成活代码）；
  找键名要锚定 `^KEY=`（否则正则会悄悄多要一个字符，键在也判缺）。
  完整案例见 `references/checks.md` 的 M6–M10。

## 判失败怎么办

1. **先看「实际值」那一行**，别急着改代码 —— 先分清是**实现错**还是**期望错**。
   `references/checks.md` 每项都写了「已知误报风险」，先对着看一眼。
2. 确认是误报 → **改 `references/checks.md` 的判据，再同步改 `scripts/check.sh`**，
   两处必须一起动（真源在 md，脚本是实现）。
3. 确认是真问题 → 按项目规矩改（`AGENTS.md`），改了之后**重跑整轮**。
4. 同一项反复失败 → **停下来报告**：说清试了什么、报什么错、判断的原因，不循环重试。

## 这个 Skill 不管的事

- **不动产品代码**：它只做检查，不修 bug。
- **不部署**，不碰控制台配置。
- **不做流水线**（已定；理由见「已定事项」）。

## 已定事项（不要再问）

- **不接 CI / 发布流水线**（Day 25 拍板）。理由：20 项里有 5 项要公网、2 项要 `tcb` 登录、
  1 项要本地服务，放进 CI 只能是残缺版；而且这份检查的重点是**人看「实际值」**，
  不是等一个绿勾。它的定位就是**手工跑的发布前体检**。

## 未定事项（碰到了问用户，不要自己定）

1. `read` / `write` 的 `CLOUDBASE_API_KEY` 缺了报的是 `DB_AUTH_FAILED`，要不要加 `checkEnv` 让它更直白。
2. 第 19 项对 `DUPLICATE` 这类「非字面量形式」的错误码仍抓不到，值不值得写更重的检查。
3. 第 10 项（拦截页）只定性到 `Sec-Fetch-Mode: navigate`，**机制来源未查清**，换环境可能复发。
